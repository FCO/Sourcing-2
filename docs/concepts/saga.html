Sagas

A saga is a long-running business process that coordinates commands across multiple aggregations. Unlike an aggregation (which is a single consistency boundary), a saga spans multiple aggregations and manages the workflow between them using the Saga pattern.

What Sagas Are

Sagas are the solution to a fundamental distributed systems problem: how do you maintain consistency across multiple services when atomic transactions aren't available?

  • They coordinate multiple aggregations in a single business workflow
  • They maintain a state machine that tracks progress through the process
  • They implement compensation — if any step fails, previously completed steps are rolled back
  • They support timeouts for long-running processes that might stall

Why Use Sagas

In traditional monolithic applications, you could wrap multiple changes in a single database transaction. In distributed systems, this isn't possible — each service owns its data. The Saga pattern provides an alternative:

ApproachDescriptionTrade-off
Distributed TransactionsTwo-phase commit across servicesRequires all services to support it; can block indefinitely
Saga PatternSequential local transactions with compensationEventual consistency; compensation must be designed up-front

Sagas are ideal for:

  • Order processing — Validate payment, reserve inventory, schedule shipping
  • Account transfers — Withdraw from source, deposit to destination
  • Onboarding flows — Create user, send welcome email, provision resources
  • Any multi-step business process that spans service boundaries

Declaring a Saga

Use the saga keyword to declare a saga class. Sagas are built on top of aggregations, so they inherit all aggregation capabilities plus additional saga-specific features. Sagas are event-driven: they react to events through apply handlers, which source the aggregates they coordinate and issue commands to them. Each apply returns the saga's next state.

use Sourcing;

saga BookingSaga {
    has Str $.saga-id is projection-id;
    has Str $.state   = 'pending';

    # React to a booking request: reserve the room and open the booking.
    multi method apply(BookingRequested (:$room-id, :$booking-id, |)) is on-state('pending') {
        sourcing(Room,    :$room-id).reserve: :$booking-id;
        sourcing(Booking, :$booking-id).open;
        'awaiting-payment'
    }

    multi method apply(PaymentReceived (:$booking-id, |)) is on-state('awaiting-payment') {
        sourcing(Booking, :$booking-id).confirm;
        'confirmed'
    }

    # The declarative inverse of a booking request — see Compensation below.
    multi method anti-event(BookingRequested (:$room-id, :$booking-id, |)) {
        sourcing(Room,    :$room-id).released: :$booking-id;
        sourcing(Booking, :$booking-id).cancelled;
    }
}

The canonical way to drive a saga is to rebuild it from its history and apply the new event live, then persist the event so later reconstructions replay it:

my $saga = sourcing BookingSaga, :$saga-id;   # rebuild from history
$saga.apply($event);                          # react live
$*SourcingConfig.emit: $event;                # persist for replay

State Machine and Per-State Dispatch

Sagas use a declarative state machine. Each apply method returns its resulting state (with the return-type syntax --> 'state-name' or simply by returning the string), and the saga tracks the current state in $.state.

On an apply candidate the is on-state(...) trait is a dispatch key, not a guard: a saga may declare several apply candidates for the same event type, each tagged with a different state, and the framework runs the one whose tag matches the current state. on-state accepts a single state, a list (<a b>), or a junction ('a' | 'b', none <done failed>). (On a non-apply method such as a command, the same trait is instead a runtime guard that throws when called in the wrong state.)

multi method apply(PaymentReceived (:$booking-id, |)) is on-state('awaiting-payment') {
    sourcing(Booking, :$booking-id).confirm;
    'confirmed'
}

# A second candidate for the SAME event in a later state — a duplicate or late
# payment after the booking is already confirmed is a deliberate no-op.
multi method apply(PaymentReceived $) is on-state('confirmed') { }

An apply candidate without an on-state tag is a wildcard that runs in any state; tagged candidates take precedence, and the most specific event type wins (so a catch-all apply(Any) never shadows a specific handler).

No matching candidate ⇒ rollback

If an event reaches the saga and no apply candidate matches the current state, it is treated as a protocol violation: the saga rolls back (emitting its queued anti-events) and moves to the 'failed' state. To accept an event in a state on purpose — for example to ignore a benign duplicate — declare a no-op candidate with the matching is on-state(...), as shown above.

Compensation and Rollback

Compensation is declarative. For an event the saga reacts to, declare an anti-event handler that builds the inverse — the event(s) that undo what the reaction did:

multi method apply(BookingRequested (:$room-id, :$booking-id, |)) is on-state('pending') {
    sourcing(Room,    :$room-id).reserve: :$booking-id;   # reserve the room
    sourcing(Booking, :$booking-id).open;                 # open the booking
    'awaiting-payment'
}

# Its inverse: release the room and cancel the booking.
multi method anti-event(BookingRequested (:$room-id, :$booking-id, |)) {
    sourcing(Room,    :$room-id).released: :$booking-id;
    sourcing(Booking, :$booking-id).cancelled;
}

On every apply, the framework runs the matching anti-event (under replay, so it only builds the inverse events without emitting them) and queues them. On rollback the queued inverses are emitted in reverse order. Because the queue is rebuilt from apply on every reconstruction, compensation survives reload with no extra persistence — and no manual bookkeeping.

Rollback happens automatically when:

  1. any method throws an uncaught exception (the saga rolls back and transitions to 'failed'), or
  2. an event arrives that no apply candidate handles in the current state, or
  3. you call self.rollback explicitly — typically from an apply handler for a failure or timeout event.
# Drive rollback from an event — purely event-driven.
multi method apply(PaymentTimedOut $) is on-state('awaiting-payment') {
    self.rollback;   # emits the queued anti-events in reverse order
    'cancelled'
}

rollback is idempotent and replay-safe: it emits the inverses only when running live (during replay the inverses are already in the stream), and a second call is a no-op.

anti-event uses emit methods, not commands

An anti-event handler sources the aggregate and calls its emit method (e.g. released), not its command (e.g. release). This is on purpose: a compensation undoes a fact that already happened, so it emits the inverse directly and bypasses the forward command's validation, which exists to protect forward operations.

Undo Blocks (escape hatch)

For one-off cases where a declarative anti-event doesn't fit, you can still register an undo block — a callable executed directly during rollback. Unlike anti-event, undo blocks are not rebuilt on reconstruction, so prefer anti-event for durable compensation and reach for undo only as an escape hatch.

multi method apply(TransferExecuted $e --> 'depositing') {
    $!from-account.withdraw: $!amount;
    # The block receives the saga as $_, enabling method chaining.
    $.undo: *.from-account.deposit: $!amount;
}

Undo blocks and queued anti-events share the same LIFO stack, so mixed registrations still unwind in reverse order during rollback.

Timeout Handling

Long-running processes need timeouts to handle failure scenarios like a service going down. Sagas support scheduled timeouts. By default, timeouts will call the rollback method to automatically undo any completed steps:

multi method apply(OrderPlaced $e --> 'waiting-payment') {
    # Schedule a timeout to cancel if payment isn't received
    # This will automatically call rollback() when it fires
    self.timeout-in: 'rollback', :5minutes;
}

You can also specify a custom timeout handler:

multi method apply(OrderPlaced $e --> 'waiting-payment') {
    # Schedule a custom timeout handler
    self.timeout-in: 'cancel-if-no-payment', :5minutes;
}

method cancel-if-no-payment() {
    self.rollback;
    $!state = 'cancelled';
}

The timeout methods are:

MethodPurpose
timeout-in($name, :5minutes)Schedule a timeout from within apply()
timeout-in('rollback', :5minutes)Schedule a timeout that defaults to calling rollback
cancel-timeout($name)Cancel a previously scheduled timeout
verify-timeouts()Check and fire expired timeouts (call periodically)
External Scheduler Required

Sagas don't run their own timers. Your application must periodically call verify-timeouts() on active sagas (e.g., every 10 seconds via a cron job or background worker).

Saga-Aggregate Coordination

Sagas can send commands to and bind aggregations for coordinated workflows:

send-command

Send a command directly to an aggregate:

method apply(OrderPlaced $e --> 'authorizing') {
    # Send payment command to the Payment aggregate
    self.send-command: Payment, { :order-id($!order-id) }, AuthorizePayment.new(:amount($e.amount));
}

bind-aggregate

Bind an aggregation attribute to the saga for lazy loading:

saga AccountTransfer {
    has Account $.from-account;
    has Account $.to-account;

    multi method apply(TransferStarted $e --> 'withdrawing') {
        $!from-account = self.bind-aggregate: 'from-account', Account, :id($e.from-id);
        $!to-account   = self.bind-aggregate: 'to-account', Account, :id($e.to-id);
    }
}

Saga Design Rules

  • Stay event-driven. React to events in apply; source aggregates and issue commands from there. Drive failure and timeout paths with events too.
  • Declare an anti-event per reaction. For every event the saga reacts to, ask: "if we roll back, what undoes this?" and declare the matching anti-event.
  • Whitelist the states an event is valid in. Use is on-state(...); add a no-op candidate where a duplicate or late event should be ignored. Anything unhandled rolls back.
  • Keep sagas idempotent. Target aggregations should handle repeated commands gracefully.
  • Use timeouts for critical paths. If a step takes too long, assume it failed and roll back.
  • Name states after user-facing outcomes. 'completed', 'cancelled', 'failed'

Example: Order Creation Saga

Event-driven throughout: each apply reacts to an event, sources the aggregates it coordinates and issues commands; each reaction declares its anti-event; failure and timeout are driven by events; and per-state dispatch keeps the flow honest.

use Sourcing;

# Saga trigger events (the saga's own stream, keyed by saga-id)
class OrderRequested  { has $.saga-id; has $.order-id; has $.total }
class PaymentTaken    { has $.saga-id; has $.order-id }
class StockReserved   { has $.saga-id; has $.order-id }
class PaymentTimedOut { has $.saga-id }

saga CreateOrder {
    has Str $.saga-id is projection-id;
    has Str $.state   = 'pending';

    multi method apply(OrderRequested (:$order-id, :$total, |)) is on-state('pending') {
        sourcing(Payment, :$order-id).charge: :amount($total);
        self.timeout-in: 'rollback', :1minute;   # auto-cancel if nothing happens
        'charging'
    }

    multi method apply(PaymentTaken (:$order-id, |)) is on-state('charging') {
        self.cancel-timeout: 'rollback';
        sourcing(Inventory, :$order-id).reserve;
        'reserving'
    }

    multi method apply(StockReserved (:$order-id, |)) is on-state('reserving') {
        sourcing(Shipping, :$order-id).schedule;
        'completed'
    }

    # A timeout (or any failure) rolls back: the queued anti-events fire in reverse.
    multi method apply(PaymentTimedOut $) is on-state('charging') {
        self.rollback;
        'cancelled'
    }

    # Declarative inverses, queued automatically and emitted in reverse on rollback.
    multi method anti-event(OrderRequested (:$order-id, |)) {
        sourcing(Payment, :$order-id).refunded;
    }
    multi method anti-event(PaymentTaken (:$order-id, |)) {
        sourcing(Inventory, :$order-id).released;
    }
}
