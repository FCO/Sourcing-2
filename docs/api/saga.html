Sourcing::Saga

A role for saga classes that coordinate long-running multi-step business processes across multiple aggregations. Sagas maintain state machines, track compensating transactions for rollback, and support timeout handling.

Note: You never use this role directly. It's automatically composed when you declare a saga using the saga keyword via Metamodel::SagaHOW.

What It Does

Sagas extend aggregations with additional capabilities for coordinating complex business workflows:

  • Declarative compensation — anti-event handlers whose inverses are queued on every apply and emitted in reverse on rollback
  • State machine with per-state dispatch — apply returns the next state; is on-state(...) selects among same-event handlers by current state
  • Timeout support — Schedule and handle timeouts for long-running processes
  • Aggregation binding — Lazy loading and tracking of related aggregates
  • Undo blocks — LIFO escape hatch for compensation that doesn't fit anti-event

How It's Used

You declare a saga using the saga keyword. It is event-driven: apply handlers react to events, source the aggregates they coordinate and issue commands; each reaction declares its inverse with anti-event. The metaclass composes the role and generates the necessary infrastructure:

use Sourcing;

saga AccountTransfer {
    has Str $.saga-id is projection-id;
    has Str $.state   = 'pending';

    multi method apply(TransferRequested (:$from-id, :$to-id, :$amount, |)) is on-state('pending') {
        sourcing(Account, :id($from-id)).withdraw: :$amount;
        sourcing(Account, :id($to-id)).deposit: :$amount;
        self.timeout-in: 'rollback', :5minutes;
        'transferring'
    }

    multi method apply(TransferConfirmed $) is on-state('transferring') {
        self.cancel-timeout: 'rollback';
        'completed'
    }

    # A timeout (or any failure) rolls back; the queued inverse fires in reverse.
    multi method apply(TransferTimedOut $) is on-state('transferring') {
        self.rollback;
        'cancelled'
    }

    # Declarative inverse of the transfer: reverse both legs.
    multi method anti-event(TransferRequested (:$from-id, :$to-id, :$amount, |)) {
        sourcing(Account, :id($to-id)).withdrew: :$amount;
        sourcing(Account, :id($from-id)).deposited: :$amount;
    }
}

Public Methods

method start

Creates a new saga and emits a SagaCreated event to initialize the saga in the event store.

multi method anti-event(EventType $e)

The declarative compensation hook (you define it on your saga). For an event the saga reacts to in apply, declare an anti-event multi that builds the inverse — sourcing the target aggregate and calling its emit method (not its command, so it bypasses forward validation). It may produce more than one inverse event.

On every apply, the framework runs the matching anti-event under forced replay (so the emit methods only build the inverse events without emitting) and queues them. On rollback the queued inverses are emitted in reverse order. Because this runs inside apply, the queue is rebuilt on every reconstruction — compensation is durable with no extra persistence and no manual self.undo.

multi method apply(StepRequested (:$item, :$amount, |)) is on-state('open') {
    sourcing(Inventory, :$item).reserve: :$amount;
    'reserved'
}
multi method anti-event(StepRequested (:$item, :$amount, |)) {
    sourcing(Inventory, :$item).stock-released: :$amount;   # emit, not command
}

method queue-compensation(%rec)

Internal. Called by the metaclass while applying an event whose anti-event produced an inverse; pushes a deferred re-emit block (carrying the built event, its target type and ids) onto the rollback stack. You normally don't call this directly.

method undo(Callable $block)

Escape hatch for compensation that doesn't fit anti-event. Stores a callable on the same LIFO stack used by queued anti-events; during rollback the block is executed directly (it receives the saga as the topic $_, allowing method chaining). Unlike anti-event, undo blocks are not rebuilt on reconstruction, so prefer anti-event for durable compensation.

# After withdrawing from an account, register the undo block
$!account.withdraw: 100;
$.undo: *.account.reverse-withdraw: 100;

# During rollback, this block executes:
# $!account.reverse-withdraw: 100;

method timeout-in(Str $method-name, *%params)

Schedules a timeout that fires after a specified duration. If no method name is provided (or if the method name is 'rollback'), the default rollback method will be called when the timeout fires:

  1. Computes scheduled-at = DateTime.now.later(|%params)
  2. Adds to %!timeout-handlers
  3. Adds to @!timeout-schedule (keeping it ordered)
  4. Emits TimeOutScheduled event

Default behavior: If you call self.timeout-in: 'rollback', :5minutes or simply don't specify a method name that exists, the timeout will automatically call self.rollback when it fires. This is useful for automatically canceling long-running processes that exceed their time limit.

Note: Can only be called from within an apply() method.

method rollback()

Emits the queued anti-events (and runs any undo blocks) in reverse order, then clears the stack. Idempotent and replay-safe: a second call is a no-op, and the inverses are emitted only when running live — during replay they are already in the stream. Called automatically when a method throws an uncaught exception (the saga also moves to 'failed') or when an event reaches the saga that no apply candidate handles in the current state; you may also call it explicitly, typically from an apply handler for a failure or timeout event.

method verify-timeouts() is command

Iterates over the ordered timeout schedule. While the next entry's DateTime is <= DateTime.now, emits TimedOut events. Should be called periodically (e.g., every 10 seconds) by an external scheduler.

method cancel-timeout(Str $method-name)

Cancels a scheduled timeout by name. Removes the entry from %!timeout-handlers and all entries with that method name from @!timeout-schedule.

method lookup(Sourcing::Saga:U $type, *%ids)

Retrieves a saga by ID from the event store. Returns a new saga instance with all events applied.

method send-command(Mu $aggregate-type, %ids, Mu $command)

Sends a command to an aggregate. Emits a command event to the event store directed at the specified aggregate type.

method bind-aggregate(Str $attr-name, Mu $aggregate-type, %ids)

Binds an aggregate reference to the saga and emits a SagaAggregationBound event to track the relationship in the event store.

How Timeout Scheduling Works

  1. Scheduling — Call self.timeout-in: "handler", :5minutes inside apply()
  2. Replaying — apply(TimeOutScheduled) restores the schedule from the event store
  3. Firing — External scheduler calls verify-timeouts() periodically
  4. Handling — apply(TimedOut) looks up the handler and dispatches to it
  5. Canceling — Call self.cancel-timeout("handler") to remove

State Machine and Per-State Dispatch

Each apply method returns its resulting state (via --> 'state-name' or by returning the string). The saga tracks the current state in $.state.

On an apply candidate the is on-state(...) trait is a dispatch key: a saga may declare several apply candidates for the same event type, each tagged with a different state (a single state, a list, or a junction), and the framework runs the one matching the current state. Untagged candidates are wildcards; tagged candidates and the most specific event type win. If no candidate matches the event in the current state, the saga rolls back and moves to 'failed' — declare a no-op candidate to accept (and ignore) an event in a state on purpose. On a non-apply method (typically a command), the same trait is a runtime guard that throws when the method is called in a disallowed state.
